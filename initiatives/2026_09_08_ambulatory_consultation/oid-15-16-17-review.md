# APP-02: проверка смысла OID .15, .16, .17

Дата: 22.09.2026. Исследование источников, без изменения профилей и преобразователя.

## Результат

Общая таблица консультации и патологоанатомического исследования:
- .15 — идентификатор случая оказания медицинской помощи в экземпляре МИС.
- .16 — идентификатор стационарного случая (номер истории болезни).
- .17 — два назначения: посещение в рамках амбулаторного обращения и амбулаторный случай (номер амбулаторной карты). Одного окончания OID недостаточно для универсального определения сущности.

Конкретное требование У1-22 протокола консультации уточняет второй id: .16 содержит номер истории болезни, .17 — номер амбулаторной карты. Первый id с .15 содержит идентификатор случая. code отдельно обозначает тип карты по 1.2.643.5.1.13.13.99.2.723; medService:DocType уточняет вид документа по 1.2.643.5.1.13.13.11.1522 при типе «иная карта».

Следствие для исходного XML: .15=5469-16 — идентификатор документируемого случая (в нашей модели посещения); .17=5499-16 — номер карты. Представление первого в Encounter.identifier и второго в Encounter.partOf.identifier имеет опору в требованиях источника. Классификация identifier.type по типу карты — отдельное соглашение FHIR-маппинга, а не прямое требование CDA. Сам экземпляр карты для логической ссылки не обязателен. СПО источник не задаёт.

Независимая нумерация разных видов карт: проверенные требования не задают специальных OID для карт беременности и т.п. В руководстве патологоанатомического исследования, с. 16, сноска 3 разрешает дополнительные дочерние узлы при недостаточной уникальности. Это подтверждает необходимость различать пространства идентификаторов, а не полагаться только на type. Применимость такого допуска к современным редакциям и строгим инвариантам RuCore требует отдельной проверки.

Историческая находка: 21.10.2024 в обсуждении #279 Е. Коган уже предложил передавать тип карты как тип её номера при ссылке без экземпляра карты. Тогда использовалась ссылка episodeOfCare; текущая предлагаемая модель использует partOf.
