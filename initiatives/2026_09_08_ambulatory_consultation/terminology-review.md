В FHIR R5 `example` — иллюстративная подборка внешних кодов, `fragment` — управляемая часть с определёнными назначением и границами, `not-present` — отсутствие concept, `complete` — весь состав. Поэтому замена всего на fragment также была бы недостоверной. Для внешних справочников без обязательства сопровождать коды предпочтителен not-present; проверяемые локальные фрагменты можно вести отдельно в рамках явной политики сопровождения.

## Общие изменения

1. Добавить политику терминологий: критерии content; владелец и источник; дата/версия исходной выгрузки; canonical ↔ OID; правила обновления и проверки полноты. Не считать версию выпуска IG версией НСИ. Сохранить существующие canonical URI; не менять Coding.version механически.
2. Для поддерживаемого полного снимка фиксировать исходный файл/хеш и проверять состав, включая иерархии и исключённые/неактивные коды. Отличать собственные группирующие коды RuCore от концептов НСИ; не заявлять идентичность систем, если состав семантически изменён.
3. `include codes from system` сохранить там, где смысл ValueSet — все коды источника. Fragment не превращает эту формулу в конечный список опубликованных concept. Не заменять её перечислением нескольких кодов ради успешного expansion: это сузит контракт.
4. Приоритет полных данных — required-привязкам и дискриминаторам, особенно coverageDocument. Их работоспособность не должна зависеть от догадки сервера о составе внешнего справочника. Остальные внешние системы могут оставаться неполностью проверяемыми согласно описанной политике.
5. RelatedPerson_Relationship содержит явные коды двух внешних OID-систем без локальных CodeSystem. Определить источник проверки: зависимость на терминологический пакет либо правдивые метаданные систем (not-present без списка; fragment/example только по действительному содержанию). NamingSystem сам по себе не заменяет определения кодов. Не переименовывать системы этого ValueSet без отдельного решения о миграции.
6. В примерах сверить пары system/code/display с источниками. Не объявлять все коды корректными после снятия ложного complete. Отдельные ошибки стандартных кодировок (например, RUB как UCUM и CONS в encounter-type из старого QA) исправляются в самих примерах, не правкой стандартных CodeSystem.
7. Не добавлять внешний OID справочника как идентификатор ValueSet только ради предупреждения о неназначенном OID: кодовая система и набор значений — разные артефакты.

## Как работать с Publisher

Неполнота определения кодов и невозможность expansion — допустимое ограничение ресурса not-present, а не основание приписывать ему complete. Для полной проверки нужен локальный/зависимый терминологический пакет или сервер, знающий точные canonical URI и версии. Ссылка на веб-страницу НСИ не заменяет такой сервис.

Первый прогон после исправлений — без новых подавлений. Сохранить точные message ID, URI и уровни сообщений; отличать отрицательную проверку кода от отсутствия возможности проверки. При намеренно неполной внешней терминологии допустимо документировать ожидаемый warning и, при необходимости, точечно подавить именно его с причиной. Не подавлять классы ошибок Unknown code целиком. input/ignoreWarnings.txt сейчас содержит только шаблон.

`no-expansions-files` управляет созданием файлов expansion; это не доказанное средство отключить все запросы $expand или исправить проверку кодов. `-tx n/a` пригоден для отдельного структурного прогона, но не подтверждает терминологическую валидность. После смены состава справочников повторять диагностический прогон с чистым/изолированным txcache, сохранив прежний для сравнения.

## План проверки реализации

1. Зафиксировать инвентарь и правила; удалить три заглушки, честно классифицировать частичные списки, проверить малые полные справочники.
2. SUSHI, затем локальный Publisher на фиксированных версиях инструментов и зависимостей. Сравнить QA до/после по категориям, а не только числу ошибок.
3. Для complete проверить известный код и заведомо отсутствующий; для not-present убедиться, что «не удалось проверить» не выдается за «код корректен»; проверить раскрытие ValueSet и распознавание coverageDocument.
4. Добавить небольшую автоматическую проверку терминологических артефактов: not-present без concepts, отсутствие тестовых заглушек, complete со свидетельством полноты для внешних источников. Сверка полноты требует источника, одного анализа FSH недостаточно.
5. Изменения профилей и ослабление binding strength не использовать как обход ошибок терминологической инфраструктуры. После предметного согласования — реализация отдельным коммитом без публикации; обновление ГОСТ остаётся за границей текущей экспериментальной ветки.
