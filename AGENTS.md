# AGENTS

## Назначение репозитория

Этот каталог `/Users/ekogan/git3/RuCoreIG` содержит исходники RuCore.

- Основной рабочий цикл: локальные изменения -> `git push` в GitHub-репозиторий `fhir-ru/RuCoreIG`.
- В GitHub-репозитории работает автопаблишер.
- CI-публикация выкладывается на `https://build.fhir.org/ig/fhir-ru/RuCoreIG/`.
- Для проверки актуального CI-билда по умолчанию ориентироваться именно на `build.fhir.org`, а не на сторонние зеркала.

## Политика версий

- При содержательном изменении спецификации поднимается минорная версия: `0.5.0` -> `0.6.0`.
- При редакторских правках, уточнениях формулировок, исправлении опечаток и иных несодержательных изменениях поднимается patch-версия: `0.5.0` -> `0.5.1`.
- Главный номер версии (`1.0.0`, `2.0.0` и т.д.) меняется только по явному указанию.
- Для каждого изменения версии обязательно обновлять комментарий в истории версий.

При изменении версии необходимо синхронно проверять и обновлять:

- `sushi-config.yaml`
- `package-list.json`
- `input/pagecontent/index.md`
- `input/pagecontent/history.md`

После изменения версии желательно убедиться, что сгенерированный `ImplementationGuide` тоже отражает ту же версию.

## Правила для RuCore и ГОСТ

В этой же локальной папке ведется разработка текста ГОСТ.

- Публикуемые Markdown-исходники глав ГОСТ хранятся в `input/pagecontent/gost-*.md`.
- Инфраструктура сборки ГОСТ хранится в `gost/`.
- Публикуемый DOCX хранится в `input/assets/gost/GOST_Interoperability.docx`.
- Локальные справочные материалы и промежуточные файлы хранятся в исключенном из Git каталоге `gost-local/`.
- ГОСТ публикуется как отдельный раздел сайта RuCore, но сохраняет явную маркировку проекта стандарта.
- Файлы ГОСТ находятся в этом репозитории для синхронной работы со спецификацией RuCore.
- При изменениях в RuCore важно синхронизировать с ними текст ГОСТ.
- При изменениях в тексте ГОСТ важно проверять, не расходится ли он с текущими FSH-исходниками RuCore.

## Практические правила работы

- Перед коммитом изменений в FSH нужно запускать `bash run_sushi.sh` и читать файл `sushi_output.txt`.
- Если неочевидно, является изменение содержательным или редакторским, нужно спросить пользователя перед изменением версии.
- При редактировании спецификации RuCore необходимо проверять, какие документы из папки `development_policy/` применимы к данному изменению, и следовать зафиксированным в них политикам.
- Если выполненная задача дает изменение, достойное упоминания в версии, перед коммитом нужно актуализировать `input/pagecontent/history.md`.
