# 6. Информационные ресурсы

Настоящий раздел содержит унифицированное представление профилей RuCore в стиле ПНСТ 995-2024.

Для каждого профиля приводится snapshot-представление с указанием ограничений и уточнений, внесенных профилем. Общесистемные элементы принимаются по приложению А настоящего документа.

## 6.1 Профиль `Core_Address`

### 6.1.1 Область применения и использования

Профиль `Core_Address` предназначен для представления адресов объектов, расположенных на территории Российской Федерации, в тех случаях, когда требуется не только текстовое описание адреса, но и его привязка к отечественным классификаторам и адресным справочникам.

При профилировании приняты следующие решения. Для адресных объектов, расположенных на территории Российской Федерации, введено расширение ФИАС, позволяющее передавать идентификаторы ФИАС. Для региональной принадлежности адреса введено расширение кода региона Российской Федерации, связанное со справочником регионов Российской Федерации. Для указания назначения адреса введено расширение типа адреса, поскольку базовый атрибут `Address.use` не покрывает в полном объеме различия между адресом регистрации, проживания и иными вариантами использования адреса, принятыми в российских сценариях обмена. Для адресов вне территории Российской Федерации применяется базовый тип данных `Address` без требования соответствия профилю `Core_Address`.

## 6.2 Профиль `Core_CareTeam`

### 6.2.1 Область применения и использования

Профиль `Core_CareTeam` предназначен для описания бригады или иной группы участников оказания медицинской помощи в тех случаях, когда для профилируемых в RuCore типов участников требуется использовать согласованную российскую модель описания.

При профилировании принято решение сохранить все допустимые в FHIR R5 типы `participant.member`, а для тех типов ресурсов, для которых определены профили RuCore, требовать использование именно этих профилей. Такое решение сохраняет совместимость с базовой спецификацией и одновременно обеспечивает единый способ описания участников в российских реализациях.

## 6.3 Профиль `Core_Composition`

### 6.3.1 Область применения и использования

Профиль `Core_Composition` предназначен для представления клинических и организационных документов, в которых необходимо согласованно описывать автора, лицо, придавшее документу юридическую силу, и организацию-хранителя по единым российским правилам, не теряя при этом допустимые возможности ссылок, предусмотренные FHIR R5.

При профилировании приняты следующие решения. Для идентификатора набора версий документа, соответствующего `ClinicalDocument.setId`, введен необязательный срез `identifier:misDocumentSet`, распознаваемый по семантическому коду `mis-document-set` в `Identifier.type`. Его `system` имеет точный вид `urn:oid:1.2.643.5.1.13.13.12.2.{субъект РФ}.{организация ФРМО}.100.{МИС}.{экземпляр МИС}.50`; дочерние узлы после `50` не допускаются. `ClinicalDocument.id` с типовым узлом `51` относится к `Bundle.identifier`, а `ClinicalDocument.versionNumber` — к базовому `Composition.version`, для которого дополнительных российских ограничений не установлено. Элемент `subject` не сужается относительно `Reference(Any)`. Для `author` и `attester.party` сохранены допустимые в R5 типы ссылок, а хранитель документа ограничен профилем `Core_Organization`.

## 6.4 Профиль `Core_Coverage`

### 6.4.1 Область применения и использования

Профиль `Core_Coverage` предназначен для представления сведений о страховом покрытии и иных источниках оплаты медицинской помощи в российских сценариях обмена, прежде всего в случаях, когда необходимо передавать полис ОМС как характеристику страхового покрытия.

При профилировании приняты следующие решения. Для элемента `type` установлена расширяемая привязка к российскому справочнику источников оплаты. Для `identifier` введен общий срез `coverageDocument`, предназначенный для документов-оснований оплаты медицинских услуг, и специализированный срез `omsPolicy` для идентификатора полиса ОМС. В `identifier[omsPolicy].type.coding` обязательны два уровня классификации: срез `coverageDocumentType` с фиксированным кодом `Полис ОМС` из справочника документов-оснований оплаты и срез `omsType` с конкретным видом полиса по справочнику видов полиса ОМС. Поэтому при оплате по ОМС один номер передается только в `identifier[omsPolicy]` и не дублируется в `identifier[coverageDocument]`. Получатель страхового покрытия ограничен профилем `Core_Patient`, что обеспечивает согласованное связывание данных о покрытии с пациентом.

## 6.5 Профиль `Core_DiagnosticReport`

### 6.5.1 Область применения и использования

Профиль `Core_DiagnosticReport` предназначен для представления диагностического отчета в тех случаях, когда необходимо связать результат исследования со случаем обслуживания, направлением на исследование и исполнителями по единым правилам, принятым для российских реализаций, не теряя допустимые варианты ссылок из FHIR R5.

При профилировании приняты следующие решения. ## 6.6 Профиль `Core_Encounter`

### 6.6.1 Область применения и использования

Профиль `Core_Encounter` предназначен для представления случая обслуживания в российских информационных системах как самостоятельного события оказания помощи и как элемента более крупного эпизода лечения.

При профилировании приняты следующие решения. Для идентификатора случая оказания помощи, номера стационарной карты и идентификатора амбулаторного случая или посещения введены необязательные срезы `identifier:misEncounter`, `identifier:misInpatientRecord` и `identifier:misAmbulatoryEncounter` с семантическими типами и конечными узлами OID `15`, `16` и `17`. Каждый срез имеет кардинальность `0..1`, распознается по `Identifier.type`, а `system` проверяется по точной формуле `urn:oid:1.2.643.5.1.13.13.12.2.{субъект РФ}.{организация ФРМО}.100.{МИС}.{экземпляр МИС}.{типовой узел}` без дочерних узлов. Для `subject` сохранены типы FHIR R5 `Patient` и `Group`; при ссылке на `Patient` должен использоваться `Core_Patient`. Связь с эпизодом лечения ограничена `Core_EpisodeOfCare`, организация-исполнитель — `Core_Organization`. Диагноз случая передается в `diagnosis.condition` типом `CodeableReference(Condition)`: допускается ссылка на ресурс `Condition` либо код и текст внутри `Encounter` без обязательного создания отдельного ресурса. Кодирование диагноза не ограничивается исключительно МКБ-10: МКБ-10 принимается как базовый пример, а для специализированных областей допускаются профильные классификаторы. Состояния после процедур кодируются как диагнозы, а не ссылками на `Procedure`. Роль диагноза классифицируется двумя необязательными осями в множественном `diagnosis.use` (`0..*`): структура (рубрика) по справочнику НСИ МЗ РФ `1.2.643.5.1.13.13.11.1077` и этапность по справочнику НСИ МЗ РФ `1.2.643.5.1.13.13.99.2.795`. Авторский порядок диагнозов внутри одной рубрики передается расширением `diagnosis.extension:rank`. Требование ровно одного основного диагноза в Core не устанавливается и относится к прикладным профилям СЭМД.

1. Номер стационарной карты и идентификатор амбулаторного случая или посещения передаются в идентификаторе того `Encounter`, с которым они связаны; эти значения не объявляются синонимами общего идентификатора случая.
2. Принадлежность срезу определяется семантическим кодом в `Identifier.type`; `Identifier.system` независимо проверяется инвариантом.
3. Диагноз случая может быть передан кодом и текстом внутри `Encounter` либо ссылкой на `Condition`; создание отдельного ресурса `Condition` не является обязательным требованием Core.
4. Кодирование диагноза не ограничивается исключительно МКБ-10. МКБ-10 принимается как базовый пример; для специализированных областей допускаются профильные классификаторы.
5. При наличии нескольких диагнозов ось структуры позволяет выделить основное заболевание. Требование ровно одного основного диагноза относится к прикладным профилям СЭМД и не устанавливается в Core.
6. В стационарной практике предварительный диагноз соответствует диагнозу при поступлении, заключительный клинический — выписному. Эти соответствия относятся к применению справочника этапности и не добавляют отдельных кодов.
7. Машиночитаемым источником требований профиля является `StructureDefinition` по каноническому идентификатору `https://fhir.ru/ig/core/StructureDefinition/core-encounter`.

## 6.8 Профиль `Core_Organization`

### 6.8.1 Область применения и использования

Профиль `Core_Organization` предназначен для представления организаций в тех случаях, когда необходимо использовать российские регистрационные и отраслевые идентификаторы, сведения о лицензии и административно-территориальной принадлежности.

## 6.9 Профиль `Core_Patient`

### 6.9.1 Область применения и использования

Профиль `Core_Patient` предназначен для представления сведений о пациенте в тех случаях, когда при информационном обмене требуется использовать российские идентификаторы пациента, правила заполнения ФИО и связи с отечественными справочниками и моделями адресов и организаций.

При профилировании приняты следующие решения. Для идентификации пациента введены срезы для СНИЛС, ИНН, документа, удостоверяющего личность, полиса ОМС и идентификатора пациента в экземпляре МИС. Все они распознаются по семантическому коду в `Identifier.type`, а конкретное пространство идентификатора независимо передается в `Identifier.system`. Для ИНН дополнительно обязателен стандартный код `TAX`. Для документа личности дополнительно указывается конкретный вид документа. В типе полиса ОМС дополнительно обязательны код `Полис ОМС` из справочника документов-оснований оплаты и конкретный вид полиса. Срез `misPatient` имеет кардинальность `0..1`, тип `mis-patient` и точную формулу OID ФРМО с фиксированным узлом `100` и конечным узлом `10`. Для имени уточнен порядок `name.given`: первым указывается имя, вторым — отчество. Для российских адресов применяется `Core_Address`, для иностранных — базовый `Address`. `managingOrganization` соответствует `Core_Organization`.

## 6.10 Профиль `Core_Practitioner`

### 6.10.1 Область применения и использования

Профиль `Core_Practitioner` предназначен для представления сведений о медицинском работнике в тех случаях, когда при информационном обмене требуется использовать российские идентификаторы и правила описания персональных данных.

При профилировании приняты следующие решения. Для идентификации медицинского работника введены отдельные срезы идентификатора для СНИЛС и документа, удостоверяющего личность. Такое решение позволяет явно различать виды идентификаторов и задавать для них фиксированные системы идентификации.

Для представления имени сохранена базовая модель `HumanName`, однако уточнен порядок заполнения массива `given`: первым указывается имя, вторым — отчество. Для элемента `gender` зафиксировано использование значений `male`, `female` и `unknown`; значение `other` не применяется в целях совместимости с российскими справочниками. Для элемента `address` установлено правило применения профиля `Core_Address` только для адресов на территории Российской Федерации, чтобы описание российских адресов медицинских работников подчинялось единым правилам, а иностранные адреса могли передаваться базовым типом `Address`.

## 6.12 Профиль `Core_Procedure`

### 6.12.1 Область применения и использования

Профиль `Core_Procedure` предназначен для представления сведений о выполненной медицинской процедуре в тех случаях, когда требуется использовать российскую номенклатуру медицинских услуг и согласованно профилировать ссылки на участников и субъект процедуры, не теряя допустимые варианты FHIR R5.

Для `identifier` введен срез `medicalServiceCode`, предназначенный для передачи кода услуги по Номенклатуре медицинских услуг МЗ РФ с фиксированной системой идентификации. Для `code` установлена расширяемая привязка к соответствующему набору значений номенклатуры медицинских услуг. ## 6.14 Профиль `Core_ServiceRequest`

### 6.14.1 Область применения и использования

Профиль `Core_ServiceRequest` предназначен для представления запроса на услугу или направления в тех случаях, когда необходимо согласованно описать субъект запроса, направляющее лицо, исполнителя, случай обслуживания и страховое покрытие в единой российской модели, не теряя допустимые варианты ссылок из FHIR R5.

При профилировании приняты следующие решения. Для `subject`, `requester`, `performer` и `insurance` сохранены допустимые в FHIR R5 типы ссылок; при этом для типов ресурсов, профилируемых в RuCore, должны использоваться соответствующие профили RuCore. Случай обслуживания ограничен профилем `Core_Encounter`. Такое решение позволяет использовать `ServiceRequest` как опорную точку маршрута оказания услуги без расхождения в моделях участника оказания помощи и финансового обеспечения.

## 6.15 Профиль `Core_Bundle`

### 6.15.1 Область применения и использования

Профиль `Core_Bundle` предназначен для передачи пакетов ресурсов RuCore, включая пакеты документов СЭМД. Профиль сохраняет все типы и сценарии базового ресурса `Bundle` и не фиксирует `Bundle.type`.

Для идентификатора конкретного экземпляра документа, соответствующего CDA `ClinicalDocument.id`, используется `Bundle.identifier` с семантическим типом `mis-document`. Его `system` имеет точный вид `urn:oid:1.2.643.5.1.13.13.12.2.{субъект РФ}.{организация ФРМО}.100.{МИС}.{экземпляр МИС}.51`. Базовая кардинальность `Bundle.identifier` равна `0..1`, поэтому FHIR не разрешает нарезку этого элемента. Условный инвариант применяется только при наличии типа `mis-document`; идентификатор иного типа остается допустимым.
