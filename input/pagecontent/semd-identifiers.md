# Идентификаторы СЭМД: границы текущей реализации

RuCore реализует идентификаторы из правил СЭМД только там, где их семантика однозначно соответствует элементу FHIR и уже существует подходящий базовый профиль. Динамические OID медицинской организации и экземпляра МИС передаются непосредственно в `Identifier.system` в форме `urn:oid:...`; отдельный `NamingSystem` для каждого такого OID не создается.

## Что реализовано

| Типовой узел | Значение | Представление в RuCore |
|---|---|---|
| `.15` | Случай оказания медицинской помощи | `Core_Encounter.identifier[misEncounter]` |
| `.16` | Стационарная медицинская карта | `Core_Encounter.identifier[misInpatientRecord]` |
| `.17` | Амбулаторный случай или посещение | `Core_Encounter.identifier[misAmbulatoryEncounter]` |
| `.50` | Набор версий документа (CDA `setId`) | `Core_Composition.identifier[misDocumentSet]` |
| `.70` | Роль медицинского работника в экземпляре МИС | `Core_PractitionerRole.identifier[misPractitionerRole]` |

Примеры этих срезов используют пары `root`/`extension` из исходных XML выписного эпикриза и протокола лабораторного исследования СЭМД. Строгая проверка принадлежности OID конкретной организации и МИС остается ответственностью системы СЭМД или наследованного прикладного профиля.

## Почему остальные идентификаторы пока не реализованы

| Идентификатор | Причина | Возможные действия |
|---|---|---|
| Корень Минздрава России `1.2.643.5.1.13` | Это пространство имен, а не идентификатор экземпляра ресурса FHIR | Оставить справочным правилом; при необходимости опубликовать описание пространства имен без среза `Resource.identifier` |
| Медицинская организация | В `Core_Organization.identifier[NSI-FRMO]` уже используется каноническая модель RuCore; добавление OID-среза создало бы второе представление того же смысла | Сохранить текущую модель; если обмен требует OID, отдельно утвердить его как альтернативный идентификатор и описать связь в `NamingSystem` |
| Структурное подразделение | В материалах СЭМД встречаются разные способы передачи организации и подразделения; не определены единые семантика значения и `Identifier.system` | Уточнить правило на наборе руководств СЭМД, затем добавить профиль или срез `Organization` для подразделения |
| Страховая медицинская организация | Нет принятого канонического identifier system RuCore, который однозначно обозначал бы организацию-страховщика | Утвердить источник и URI системы идентификации, создать `NamingSystem`, затем добавить срез в профиль организации |
| Медицинская лицензия | Уже покрыта `Core_Organization.qualification[medLicense].identifier`; новый срез дублировал бы существующую модель | Использовать существующий элемент; при необходимости добавить в его `NamingSystem` подтвержденный OID как альтернативное имя |
| Корень РЭМД | Это пространство документной инфраструктуры; ему нет однозначного соответствия среди идентификаторов текущих профилей | Определить, относится ли значение к репозиторию, документному `Bundle`, `DocumentReference` или иной сущности, и только после этого профилировать выбранный ресурс |
| СНИЛС | Уже покрыт срезами `identifier[snils]` и `NamingSystem` RuCore | Использовать существующую модель; не вводить параллельный СЭМД-срез |
| Корень перечня МИС, МИС и экземпляр МИС | Эти OID задают пространства имен информационных систем, а не бизнес-идентификаторы экземпляров текущих ресурсов | Оставить частью правил формирования динамических `Identifier.system`; при появлении сценария описания самой МИС рассмотреть профили `Device`/`DeviceDefinition` |
| Пациент `.10` | Существующая нарезка `Core_Patient.identifier` распознает срезы по фиксированному `system`, тогда как СЭМД формирует его динамически; безопасного discriminator пока нет | Оставить правило downstream-профилям; либо согласовать стабильный `Identifier.type` и использовать его как discriminator; либо отдельно пересмотреть slicing пациента с оценкой обратной совместимости |
| Документ `.51` | Это идентификатор конкретной версии документа и по смыслу соответствует `Bundle.identifier`, а профиль документного `Bundle` в RuCore пока отсутствует | Создать документный профиль `Core_Bundle` и определить в нем срез после согласования модели электронного медицинского документа |
| Внутренняя ссылка `.52` | Локальные ссылки CDA не образуют один FHIR `Identifier`: в зависимости от контекста им соответствуют `Element.id`, `Reference` и другие элементы | Описать правила преобразования CDA в руководстве по маппингу; вводить отдельные ограничения только в конкретных профилях документов |

## Рекомендуемый порядок продолжения

1. Создать документный профиль `Bundle` и реализовать `.51`, когда будет утверждена модель электронного медицинского документа.
2. Собрать примеры `.10` из нескольких актуальных СЭМД и выбрать устойчивый discriminator без изменения смысла существующих срезов пациента.
3. Отдельно согласовать канонические identifier systems для подразделения и страховой медицинской организации.
4. Описать `.52` в правилах CDA-to-FHIR mapping, а не как универсальный срез `Identifier`.
